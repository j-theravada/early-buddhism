# 動画一覧のサーバーページング化 設計仕様

## 状態

- 2026-07-17 承認済み
- `2026-07-17-search-discoverability-design.md` の「設計2: 全法話への静的HTMLリンク経路」を置き換える
- 同設計書の文字起こし全文SSRと公式アーカイブ識別は変更しない

## 目的

`/talks` を「先頭6件のプレビューから全件ギャラリーへ差し替える画面」と「検索エンジン向け静的アーカイブ」の二段構成から、ユーザーと検索エンジンが共通して使える通常のサーバーページング一覧へ一本化する。

現行画面では、初期HTMLに先頭6件だけを表示し、画面下の監視位置へ近づいた後に `/api/talk-gallery` から全901件を取得している。検索欄は取得後のギャラリー内にあるため、特にモバイルでは動画一覧を開いた直後に検索できない。さらに、全件一覧とは別に `/talks/archive/[page]` が存在し、同じ法話集合に二つの閲覧体験がある。

## 成功条件

- `/talks` を開いた初期HTMLに、検索フォーム、絞り込み、結果件数、当該ページのカード、ページ移動リンクが含まれる。
- JavaScriptを実行しなくても検索、絞り込み、ページ移動、詳細ページへの移動ができる。
- 通常一覧は30件ずつ表示し、ブラウザへ901件分のギャラリーJSONを送らない。
- `query`、`collection`、`series` は全件へ適用してからページを切り出す。
- 文字起こし検索の一致判定、並び順、スニペット、該当cueへのリンクを維持する。
- 現行の年代別見出しと年代ジャンプを、通常リンクとして維持する。
- 詳細ページから検索条件と元のページ番号を保って一覧へ戻れる。
- 全法話へ通常のHTMLリンクだけで順次到達でき、ページ一覧URLをサイトマップへ含める。
- 旧アーカイブURLをリンク切れにしない。

## 非対象

- 文字起こしデータの生成方法とSRT修正フローは変更しない。
- 現行検索の語句正規化、AND条件、日付順などの検索意味論は変更しない。
- 月例講演会など、コレクション専用の検索流入ページは作らない。
- 無限スクロール、「さらに読み込む」、入力中の即時検索は残さない。
- 検索順位そのものは完了条件にしない。

## 検討した方式

### 1. 完全なサーバーページングと送信式検索（採用）

検索・絞り込み・ページングをServer Component側で処理し、現在ページの30件だけをHTMLとして返す。GETフォームと通常リンクを使うため、初期表示、戻る・進む、URL共有、クロールの挙動が同じになる。

### 2. サーバーページングと入力中のクライアント検索

一覧表示は軽くできるが、入力中のAPI要求、競合する応答のキャンセル、履歴更新、ローディング表示が必要になる。検索だけ再びJavaScript依存になり、二種類の状態管理が残るため採用しない。

### 3. 現行ギャラリーを維持して検索欄だけ先に表示

変更量は小さいが、全901件の取得、仮想スクロール、プレビューから全件一覧への差し替えが残る。「普通にページングする」という今回の目的を満たさないため採用しない。

## URL設計

### 一覧URL

- 1ページ目: `/talks`
- 2ページ目以降: `/talks/page/2`、`/talks/page/3`、…
- 1ページ30件
- 並び順は現行ギャラリーと同じ新しい順
- `/talks/page/1` はNext.jsのroute到達前redirectで `/talks` へ308リダイレクトし、認識済みquery parameterを保持する
- ページ番号は先頭ゼロのない10進正整数だけを受け付け、0、負数、`02`、`2.0`、指数表記、整数でない値、絞り込み後の総ページ数を超える値は404
- 1ページ目で該当0件の場合は、検索条件と0件表示を含む正常な結果画面を返す

パスでページ番号を表すのは、検索条件のクエリ文字列とページ位置を分離し、一覧の正規URLを明確にするためである。

### 検索・絞り込みパラメータ

既存の外部・内部リンクとの互換性を守るため、次のGETパラメータ名を維持する。

- `query`: 検索語。前後空白を除去し、現行APIと同じ最大120文字に正規化する
- `collection`: コンテンツ分類ID
- `series`: シリーズID

collection/seriesはparserの戻り値だけで有効判定しない。特にseries parserは未知の動的IDも受理するため、全法話から作った利用可能ID集合とcollection-series親子関係の両方に照合する。未知IDと矛盾する組み合わせは404とし、正しい条件で検索結果が0件になった場合は200とする。

検索フォームは `method="get"` とし、Enterまたは検索ボタンで実行する。選択中のcollection/seriesはhidden inputで保持し、現在の絞り込み内を検索する。検索実行、分類変更、シリーズ変更、条件解除では必ず `/talks` へ戻る。ページリンクだけが現在の条件を維持して `/talks/page/N` へ移動する。

フィルタ操作は現行の組み合わせ規則を維持する。

- collection変更はqueryを保持する
- `scripture_commentary` 以外のcollectionを選ぶ時はseriesを解除する
- seriesを選ぶ時はcollectionを `scripture_commentary` にする
- 選択済み条件の×はその条件だけを解除し、「すべて解除」はqueryを含む全条件を解除する

同じ条件から常に同じURLを生成できるよう、内部リンクではパラメータ順を `query`、`collection`、`series` に統一し、空値はURLへ含めない。

### 詳細ページから戻るURL

既存の詳細URL用パラメータにページ位置を追加する。

- `galleryQuery`
- `galleryCollection`
- `gallerySeries`
- `galleryPage`（新規。1は省略可能）

一覧カードから詳細ページへ移動する際に現在の状態を渡し、詳細ページの「動画一覧へ戻る」は同じ検索条件・ページへ戻す。不正な `galleryPage` は1として扱う。通常のカードリンクだけでなく、文字起こしスニペットからcueへ移動するリンクにも `galleryPage` を渡す。

## サーバー側データフロー

一覧ページ固有の処理をPage Componentへ直書きせず、application層の共有サービスへ集約する。

```text
URLのpage/query/collection/seriesを解析
  -> 全法話の軽量ギャラリーデータを新しい順で取得
  -> queryがある時だけ文字起こし検索データを読み込む
  -> 検索の一致IDを求める
  -> collection/seriesを適用
  -> 該当総件数と総ページ数を計算
  -> 現在ページの30件をslice
  -> 現在ページの一致法話だけスニペットを生成
  -> Server ComponentでHTMLを返す
```

### 検索サービスの分離

現行 `/api/talk-search` にある検索データ構築と実行を、ルートに依存しないserver-onlyサービスへ移す。

現行実装は一致した全法話のスニペットまで一度に生成する。サーバーページングでは次の二段階へ分ける。

1. 全件から一致する法話IDを求め、現行の日付順と検索意味論を維持する。
2. 絞り込みとページ切り出し後、表示対象30件についてだけスニペットとcue情報を生成する。

検索語が空の場合は約90MBの `transcript-search-documents.json` をimport・parseしない。検索時だけ遅延ロードし、同一サーバープロセス内では既存と同様に再利用できる形にする。

一致IDの計算結果は、現行APIと同じく正規化済みqueryをキーに5分間・最大100件までプロセス内でキャッシュする。キャッシュには全件分のスニペットを持たせず、順序付きの一致IDだけを保持する。スニペットはキャッシュされた一致IDを絞り込み・ページ分割した後、現在ページ分だけ生成する。

### ページ結果の型

共有サービスは少なくとも次を返す。

- 正規化済み条件
- 現在ページ番号
- 総件数
- 総ページ数
- 現在ページの `TalkGalleryItem[]`
- talk IDをキーとする現在ページ分の文字起こしスニペット
- 利用可能なcollection/series選択肢

Page Componentはこの結果を表示するだけにし、検索アルゴリズムとページ番号検証を持たない。

## 表示設計

### 初期HTMLに含めるもの

- 見出し「動画一覧」
- 検索入力、検索ボタン、条件解除
- collection/seriesの絞り込みリンク
- 「全N件中 A〜B件」の結果位置
- 条件なし一覧での年代ジャンプ
- ページ内の年代別見出し
- 30件以下の法話カード
- 現在ページ、前後、必要なページ番号リンク

カードの見た目と文字起こしスニペット表示は維持する。collection/seriesチップはクライアントのクリックハンドラではなく、条件付き一覧へ移動する通常のリンクにする。

検索領域は現行と同じくスクロール時に上部へ残る。年代別見出しは現在ページ内で年代が変わる位置へ表示する。条件なし一覧の年代ジャンプは、各年代の先頭法話を含むページとページ内アンカーへの通常リンクに置き換える。検索・絞り込み中は現行どおり年代ジャンプを表示しない。

ページ移動は通常のナビゲーションとしてページ先頭から表示する。Virtuoso用のスクロール位置snapshotとsessionStorage復元は削除する。

### ページナビゲーション

- 前後リンクは常に隣接ページへ移動する
- 1ページしかない時はナビゲーションを表示しない
- 多数のページ番号を一度に並べず、先頭、末尾、現在位置周辺を省略記号付きで表示する
- 各リンクは `query`、`collection`、`series` を維持する
- `prefetch={false}` を使い、30件分のRSCを多数のページについて先読みしない

## SEOとクロール

- 条件なしの `/talks` と `/talks/page/N` は、それぞれ自分自身をcanonicalにする。
- 各ページから前後ページへ通常の `<a href>` でリンクする。
- サイトマップには条件なしの `/talks` と全有効ページを含める。
- `query`、`collection`、`series` のいずれかを含むURLはサイトマップへ含めず、`noindex, follow` とする。任意の検索語・組み合わせによるURL増殖を検索対象にしないためである。
- 条件付きURLはcanonicalを宣言せず、条件なしページのself-canonicalと混同させない。
- 0件になる無効な分類・シリーズ組み合わせは、検索語だけの0件表示とは異なり404を返す。

Google Search Centralも、ページ分割した各ページに固有URLとself-canonicalを持たせ、リンクで順番に接続し、フィルタURLのインデックスを避けるよう案内している。

## 旧アーカイブURLの互換性

`/talks/archive/[page]` の表示実装は削除し、サーバー側の308リダイレクトだけを残す。

旧アーカイブは100件、通常一覧は30件であるため、同じページ番号へ機械的に移すと掲載位置が大きく変わる。旧ページの先頭法話を含む新ページへ移す。

```text
targetPage = floor(((archivePage - 1) * 100) / 30) + 1
```

- targetPage 1は `/talks`
- targetPage 2以降は `/talks/page/{targetPage}`
- 旧範囲外URLは404

このリダイレクトは旧ページの全100件を一つの新ページへ対応させるものではない。旧URLを概ね同じ一覧位置へ移しつつ、最終的な発見経路は新ページ間リンクとサイトマップへ一本化する。

## 削除・置換する実装

実装完了後、参照がなくなったことを確認して次を削除する。

- `/api/talk-gallery`
- 6件プレビューから全件取得へ切り替えるloader
- `TalkGallery` のVirtuoso一覧と仮想行レイアウト
- クライアント用 `useTalkGalleryData`
- Virtuoso用ブラウザストレージと一覧固有のスクロール復元
- 旧アーカイブ表示コンポーネントと100件ページング関数
- `react-virtuoso` 依存関係

`/api/talk-search` は新しいSSR一覧以外の利用箇所がないことを検索してから削除する。検索ロジック自体は共有server-onlyサービスとして残す。

`TalkGalleryCard` が削除予定のhookからimportしている `TranscriptSnippet` 型は、削除前に `application/talk/search-api.ts` などのserver/client共通モジュールへ移す。削除予定ファイルを型だけのために残さない。

共通カード、URL builder、分類・シリーズのドメイン定義、年代別グループ化の純粋関数、文字起こし検索の純粋関数は再利用する。

## 性能上の制約

- 条件なし一覧では文字起こし検索JSONをサーバーバンドルの実行経路へ読み込まない。
- ブラウザへ送る法話データは現在ページの30件だけにする。
- Server Componentから内部HTTP APIを呼ばず、application/infrastructure層を直接利用する。
- 検索時の90MB read modelが `/talks` と `/talks/page/[page]` の両route output traceへ正しく含まれることをproduction buildで確認する。
- 現行 `/api/talk-search` 用の `outputFileTracingIncludes` / `Excludes` があれば、ビルド後の実際のroute keyを確認して両一覧routeへ更新する。1ページ目だけでなく2ページ目の検索をproduction buildで実行し、read modelのENOENTがないことを確認する。
- ローカルproduction buildと本番で、条件なし一覧のHTML/RSCサイズ、検索応答時間、cold startを測る。

検索性能が本番で許容範囲を超えた場合は、Tursoへ戻すことを先に選ばない。まず一致判定とスニペット生成の分離、遅延ロード、プロセス内キャッシュ、trace内容を検証する。

## エラー処理

- ギャラリーデータの取得失敗は既存のサーバーエラー処理へ委ね、空一覧として成功させない。
- 検索データのロードまたは検索処理が失敗した場合は、無関係な全件一覧へフォールバックせずエラーとして扱う。
- queryが正常で一致0件の場合は、検索条件を保持した0件画面と条件解除リンクを表示する。
- 無効なpage、collection、seriesは404とし、別の内容へ暗黙変換しない。
- スニペットが作れない一致法話でもカード自体は表示する。

## テスト戦略

挙動変更は失敗するテストを先に追加してから実装する。

### application層

- 901件が30件ずつ、重複・欠落なく31ページに分かれる。
- 1ページ目と最終ページの件数・範囲が正しい。
- query、collection、seriesを全件へ適用した後にページングする。
- 条件変更時のURLは1ページ目になり、ページリンクは条件を保持する。
- 検索送信は選択中のcollection/seriesを保持し、collection/series変更は現行の組み合わせ規則を維持する。
- queryなしでは文字起こし検索データloaderを呼ばない。
- queryありでは全件照合後、現在ページ分だけスニペットを生成する。
- 同じ正規化済みqueryの一致IDが期限内キャッシュから再利用され、上限を超えて増えない。
- 現行検索の一致順、AND条件、スニペットcueリンクを維持する。
- 無効なページと分類IDを区別して扱う。
- series IDを実データの利用可能集合と親collectionへ照合し、未知ID・矛盾する組み合わせと正常な0件検索を区別する。
- 通常カードとスニペットの詳細URL、一覧への戻りURLが `galleryPage` を正しく往復する。

### ページ描画

- `/talks` のサーバー描画に検索フォームと最初の30件が含まれる。
- `/talks/page/2` に正しい30件と前後リンクが含まれる。
- 検索・絞り込み済みページに結果件数、条件、該当カード、スニペットが含まれる。
- ページリンク、カード、分類チップが通常のhrefを持つ。
- 年代ジャンプが対象年代の先頭法話を含むページ内アンカーへ移動する。
- 0件検索は200、総ページ数超過と無効なfilterは404になる。
- 条件なしページはself-canonical、条件付きページはnoindexになる。
- `/talks/page/1` と旧archive URLが正しい308先を返し、`/talks/page/1` はquery/collection/seriesを保持する。
- 非正規なページ番号表記を404にし、重複URLを作らない。

### 回帰確認

- ホームの検索フォームとキーワードリンクが `/talks?query=...` で動く。
- 一覧から開いた詳細ページの戻るリンクが元ページと条件を復元する。
- 文字起こしスニペットから該当cueを開く既存挙動が維持される。
- sitemap内の一覧ページ数と実際の総ページ数が一致する。
- 削除後に `/api/talk-gallery`、Virtuoso、旧storageへの参照がない。

## 検証とデプロイ

実装後は次を実行する。

1. 新規・変更対象のテスト
2. 全Bunテスト
3. `bun run format:check`
4. `bun run lint`
5. `bun run build`
6. production buildをローカル起動し、JavaScriptなしのHTTP取得で一覧、検索、絞り込み、ページ移動、404、redirectを確認
7. 条件なし `/talks` のHTML/RSCサイズが現行より不当に増えていないことを確認
8. 1ページ目と2ページ目の検索で一致件数、ページ分割、スニペット、応答時間、read model読込を確認
9. sitemapの全一覧URLが200で、旧archive URLが想定先へ308になることを確認

mainへの統合と本番デプロイ後は、実ブラウザのモバイル幅とデスクトップ幅で次を確認する。

- ヘッダーから動画一覧を開いた直後に検索欄が見える。
- 検索、絞り込み、ページ移動、詳細から戻る操作がURLと一致する。
- JavaScript有効・無効のどちらでも同じ法話集合へ到達できる。
- 本番レスポンスのcanonical、robots、redirect、圧縮後サイズが設計どおりである。
