# 字幕修正申請・承認設計

## 目的

ログインユーザーが法話詳細の字幕 cue ごとに本文の修正を申請し、字幕管理者が審査する。承認時は表示用差分を保存せず、Google Drive の「SRTリンク」が指す同一ファイルの本文を更新する。

## 正本と公開経路

- Google Drive 上の SRT を正本とする。
- `app/generated/transcripts/*.srt` は正本から生成される配布物であり、本番アプリから直接変更しない。
- 承認後に既存の生成ワークフローを起動し、生成済み SRT と `transcript-search-documents.json` を更新する。
- サイト表示は生成物のコミットとデプロイ後に更新される。表示時の override は使用しない。

## 権限

- Clerk で認証済みのユーザーだけが申請できる。
- `privateMetadata.role === "subtitle_admin"` のユーザーだけが承認・却下できる。
- クライアントにはロール自体を公開せず、認証済みの権限確認APIから管理者かどうかの真偽値だけを返す。
- 画面の表示制御とは別に、すべての書き込み Route Handler で権限を再検証する。

## 編集単位

- SRT の物理行ではなく、番号・開始時刻・終了時刻・本文を持つ cue を単位とする。
- 初期実装で変更できるのは本文だけとする。番号と時刻は変更しない。
- 修正文は空文字、1,000文字超、空行を含む本文を拒否する。

## 状態

永続状態は `pending`、`approved`、`rejected` の3つだけとする。

- Drive 更新、競合、生成ワークフロー起動の失敗時は `pending` のままとし、管理者へその場でエラーを返す。
- Drive が既に提案文へ更新済みの場合は再実行として受理し、生成ワークフロー起動後に `approved` へ進める。
- 一件を承認したとき、同じ cue の他の `pending` 申請は `rejected` にする。
- 公開待ちは永続状態にせず、管理画面へ「サイト反映には数分かかる」と表示する。

## 承認処理

1. 申請と現在の法話データを読む。
2. 法話の現在の SRTリンクが、申請時に保存した Drive file ID と一致することを確認する。
3. Drive API で最新SRTを取得する。
4. cue番号・開始時刻・終了時刻・申請時本文が一致することを確認する。
5. 対象 cue の本文だけを置換する。他のcue、タイムコード、改行形式は維持する。
6. 置換後のSRTを再解析し、cue数と全cueの番号・時刻が変わっていないことを確認する。
7. Drive API `files.update` で同一 file ID の内容を更新する。
8. GitHub Actions の生成ワークフローを起動する。
9. 申請を `approved` にし、同じcueの他の申請を `rejected` にする。

Drive更新後に後続処理が失敗しても、同じ承認操作を安全に再実行できる。最新SRTの対象本文が既に提案文なら、Driveへの再書き込みを省略して後続処理を続行する。

## 永続データ

`transcript_change_requests` は検索インデックスとは独立したDrizzle管理テーブルとし、検索seedで削除しない。

保存項目は申請ID、法話ID、Drive file ID、cue番号・開始時刻・終了時刻、申請時本文、提案本文、補足、申請者Clerk user ID、状態、作成日時、審査者、審査日時、審査メモとする。

## 外部認証

- Drive更新には `GOOGLE_DRIVE_SERVICE_ACCOUNT_JSON` を使用する。
- サービスアカウントにはSRTを置くDriveフォルダだけを編集共有する。
- 生成ワークフロー起動には `GITHUB_ACTIONS_TOKEN` を使用する。
- 認証情報はサーバー環境変数だけに置き、レスポンスやログへ含めない。
