# 初期仏教塾 検索発見性改善 設計仕様

## 目的

スマナサーラ長老の発言を調べる検索で、初期仏教塾の個別法話ページが回答根拠として発見・選択されやすい状態にする。

今回解決する問題は次の3点である。

1. 文字起こし全文が個別法話ページの初期HTMLに含まれず、検索エンジンやJavaScriptを実行しない取得系から本文が見えない。
2. `/talks` の初期HTMLには6件の個別法話リンクしかなく、残りの法話はサイトマップとクライアント描画に依存している。
3. 構造化データ上、「初期仏教塾」と運営主体の日本テーラワーダ仏教協会との関係が明示されていない。

## 成功条件

- JavaScriptを実行せずに個別法話ページを取得しても、文字起こし全文を読める。
- 通常閲覧では、初期ページサイズとDOM数を抑えた「読みやすく」表示を使える。
- 必要な時だけ「タイムライン付き」表示を読み込み、既存の時刻リンク、検索語ハイライト、指定箇所への移動を維持する。
- `/talks` から全法話へ、通常のHTMLリンクだけで最大2クリックで到達できる。
- `WebSite`、`Organization`、`VideoObject` が、日本テーラワーダ仏教協会による公式アーカイブという関係を一貫して表す。
- 現行の動画一覧検索、コレクション絞り込み、仮想スクロール、文字起こしAPIの互換性を壊さない。

## 非対象

- 月例講演会など、コレクションごとの専用ランディングページは作らない。
- 文字起こし検索APIの検索アルゴリズムや日本語分かち書きは変更しない。
- 文字起こしデータの生成・修正フローは変更しない。
- 本体WordPressサイトは変更しない。
- 検索順位の保証は行わない。今回保証するのは、検索エンジンが本文・内部リンク・運営主体を取得できる技術的条件である。

## 現状と判断根拠

- 法話は901件、生成済み文字起こしは898件ある。
- 現行の `TranscriptSection` をそのままサーバーレンダリングすると、cue単位の反復マークアップにより代表的な長時間法話で約1.0〜1.3MBのHTMLになる。
- 文字起こしを既存の `buildTranscriptParagraphs()` で段落化すると、全文テキスト部分は中央値約41KB、最大約153KBに収まる。
- `/talks` の本番初期HTMLには個別法話リンクが6件だけあり、全件取得後も `react-virtuoso` が表示領域周辺だけをDOM化する。
- 本体サイトから初期仏教塾への公開告知とリンクは既に存在する。一方、初期仏教塾側のJSON-LDは `WebSite` と `Organization` の両方を「初期仏教塾」としている。

## 設計1: 文字起こし全文のコンパクトSSR

### 採用方式

個別法話ページで該当SRTをサーバーから読み、段落化した全文をServer Componentとして初期HTMLへ出す。クライアントへ完全なcue配列は渡さない。

通常アクセス時の初期モードは「読みやすく」とする。「タイムライン付き」を選んだ時だけ、既存の `GET /api/transcripts/[id]` からcue配列を取得する。

検索結果から `transcriptCue` または `transcriptQuery` 付きで開いた場合は、従来の利用体験を守るためタイムラインを自動取得し、対象cueへのスクロールと検索語ハイライトを実行する。

### コンポーネント境界

- `app/talks/[id]/page.tsx`
  - `getTranscriptByTalkId()` で実在する文字起こしを取得する。
  - `buildTranscriptParagraphs()` で読みやすい段落を作る。
  - Server Componentの読みやすい本文をClient Componentの表示切り替えシェルへ `children` として渡す。
- `app/components/transcript-readable.tsx`（新規Server Component）
  - 段落化された全文を、見出しとAI文字起こしの注記を含む簡潔なHTMLで出す。
  - cue単位の時刻、反復クラス、イベントハンドラを持たない。
- `app/components/transcript-section-loader.tsx`
  - 「読みやすく」と「タイムライン付き」の表示状態を管理するClient Componentへ責務を変更する。
  - 初期はServer Componentの `children` をそのまま表示する。
  - タイムライン要求時だけAPI取得と動的importを行う。
  - API失敗時は読みやすい本文を残し、タイムラインを読み込めなかった旨だけを表示する。
- `app/components/transcript-section.tsx`
  - cue単位のタイムライン、時刻リンク、ハイライト、対象cueへの移動を担当する。
  - 表示モード管理と読みやすい段落生成は持たない。
- `app/api/transcripts/[id]/route.ts`
  - URL、レスポンス形、キャッシュ方針を変更しない。

### データフロー

通常アクセス:

```text
SRTファイル
  -> Server Componentで解析・段落化
  -> 初期HTMLに全文
  -> ユーザーがタイムラインを選択
  -> 既存APIからcue取得
  -> タイムライン表示へ切り替え
```

検索結果からの指定箇所アクセス:

```text
初期HTMLには段落化した全文
  -> Client Componentがcue/query指定を検知
  -> 既存APIからcue取得
  -> タイムライン表示
  -> ハイライトして対象位置へ移動
```

### エラー処理

- SRTが存在しない法話では文字起こしセクションを表示しない。
- `srtLink` があっても生成済みローカルSRTがない場合は、存在しない本文を推測表示しない。
- タイムラインAPIが404または失敗しても、SSR済みの読みやすい全文は維持する。
- API再試行の自動ループは追加しない。モードを再選択した場合のみ再取得可能とする。

## 設計2: 全法話への静的HTMLリンク経路

### 採用方式

現行 `/talks` の6件プレビュー、全件API、検索、絞り込み、仮想スクロールは維持する。その下にユーザー可視の「全法話をページ一覧で見る」リンクを1本追加する。

リンク先として `/talks/archive/[page]` を静的生成する。

- 1ページ100件
- 現在901件なので10ページ
- 現行ギャラリーと同じ並び順
- 各項目は収録日と法話タイトルを含む通常の `<a href>`
- 全ページ番号と前後リンクを全ページに表示
- 各ページはself-canonical
- `prefetch={false}` で不要な先読みを抑える
- 範囲外・不正なページ番号は404
- アーカイブページもサイトマップへ含める

これにより、全個別法話は `/talks` から最大2クリックで到達できる。

### 責務分離

- `app/application/talk/archive.ts`（新規）
  - ページサイズ、総ページ数、ページ番号検証、ページ内項目の切り出しを担う純粋関数を置く。
- `app/talks/archive/[page]/page.tsx`（新規）
  - 静的パラメータ、metadata、canonical、一覧HTML、ページナビゲーションを出す。
- `app/talks/page.tsx`
  - 現行ギャラリーの外側にアーカイブへの通常リンクを追加する。
- `app/sitemap.ts`
  - 有効なアーカイブページURLを追加する。

## 設計3: 公式アーカイブとしてのサイト識別

### 構造化データ

サイト名と運営組織を別エンティティとして表す。

```text
Organization: 宗教法人日本テーラワーダ仏教協会
  -> publisher
WebSite: 初期仏教塾
  -> contains
VideoObject: 各法話
```

- `WebSite`
  - `@id`: `https://early-buddhism.j-theravada.com/#website`
  - `name`: `初期仏教塾`
  - `url`: サブドメインのトップ
  - `inLanguage`: `ja`
  - `publisher`: 協会Organizationの `@id`
  - descriptionでスマナサーラ長老の法話デジタルアーカイブと明示する。
- `Organization`
  - `@id`: `https://j-theravada.com/#organization`
  - `name`: `日本テーラワーダ仏教協会`
  - `legalName`: `宗教法人日本テーラワーダ仏教協会`
  - `url`: `https://j-theravada.com/`
  - `logo`: 512×512の既存 `/icon-512.png`
- 各 `VideoObject`
  - `publisher` から同じOrganization `@id` を参照する。

構造化データ生成は純粋関数へ分離し、layout内へオブジェクトを直書きしない。

### 可視テキストとの一致

- 共通description:
  - `日本テーラワーダ仏教協会が運営する、アルボムッレ・スマナサーラ長老の法話デジタルアーカイブ。動画と文字起こしを検索・閲覧できます。`
- About冒頭:
  - `初期仏教塾は、宗教法人日本テーラワーダ仏教協会が運営する、アルボムッレ・スマナサーラ長老の法話デジタルアーカイブです。`
- フッター:
  - 協会リンクのラベルを `運営：日本テーラワーダ仏教協会` とする。

サイト名「初期仏教塾」と既存の各ページタイトルは維持し、不自然なキーワード追加は行わない。

## 採用しない案

### 現行タイムラインの全文SSR

実装変更は小さいが、長時間法話でHTMLが約1MBを超え、完全なcue配列がRSC payloadにも載る。大量DOMの初期生成とhydrationを招くため採用しない。

### 文字起こし専用ページ

詳細ページを軽く保てる一方、本文・内部リンク・評価が詳細ページと文字起こしページに分かれる。「個別法話ページを回答根拠にする」という目的に対して遠回りなので採用しない。

### `/talks` への全901リンク直置き

リンクだけで現行HTMLを大きく増やし、現行ギャラリーと重複する。件数増加にも弱いため採用しない。

### `<noscript>` だけの全件リンク

ユーザー可視の通常導線ではなく、JavaScriptレンダリング時に消える。クロール専用の隠し導線になり得るため採用しない。

## テスト戦略

すべての挙動変更はテストを先に失敗させてから実装する。

### 文字起こし

- 個別法話ページの初期HTMLに既知の文字起こし文が含まれる。
- 初期HTMLに `文字起こしを読み込み中です。` が含まれない。
- 文字起こしがない法話ではセクションを出さない。
- 通常アクセスの初期表示ではタイムラインAPIを呼ばない。
- タイムライン選択時だけAPIを呼び、cue IDと時刻リンクを表示する。
- cue/query指定時は自動取得し、対象cueとハイライトを表示する。
- API失敗時にもSSR済み全文が残る。

### アーカイブ

- 全901件がページ間で重複・欠落しない。
- 1ページ目は100件、最終ページは残件数だけを含む。
- 0、非数値、総ページ数超過は404。
- 各ページのcanonical、全ページ番号、前後リンクが正しい。
- `/talks` の現行6件プレビューとアーカイブリンクが両方存在する。
- アーカイブから取得した個別法話ID集合が `talks.json` と一致する。

### サイト識別

- `WebSite.name` は `初期仏教塾`。
- `WebSite.publisher.@id` と `Organization.@id` が一致する。
- `Organization.name` は `日本テーラワーダ仏教協会` であり、`初期仏教塾` ではない。
- 各 `VideoObject.publisher` が同じOrganizationを参照する。
- metadata、About、フッターの可視文言が構造化データと矛盾しない。

## 検証

実装後は次を実行する。

1. 変更対象のBunテスト
2. 全Bunテスト
3. `bun run format:check`
4. `bun run lint`
5. `bun run build`
6. production buildをローカル起動し、JavaScriptなしのHTTP取得で以下を確認
   - 代表法話ページに文字起こしの既知文が含まれる。
   - 「文字起こしを読み込み中です」がない。
   - `/talks` にアーカイブリンクがある。
   - アーカイブ全ページから全法話IDへ到達できる。
   - トップと代表法話のJSON-LDに正しいpublisherがある。

デプロイ後はSearch ConsoleのURL検査でトップ、`/talks`、代表法話をライブテストし、再クロールを依頼する。検索順位の変化は即時の完了条件にせず、表示回数・検索語・平均掲載順位を継続観測する。
